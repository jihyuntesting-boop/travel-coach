# 핵심 개념 설명

## HTML, CSS, JavaScript의 역할
- **HTML**은 화면의 구조와 내용(제목, 입력창, 버튼)을 정의한다. 이 프로젝트의 `index.html`이 해당한다.
- **CSS**는 모양(색, 배치, 반응형, 다크 모드)을 정의한다. `css/style.css`가 해당한다.
- **JavaScript**는 동작(버튼 클릭, 서버 요청, 결과 표시)을 정의한다. `js/main.js`가 해당한다.

## 입력에서 화면 반영까지의 흐름
1. 사용자가 폼을 제출하면 JavaScript가 입력값을 검사한다.
2. 통과하면 `fetch('/api/coach', {method: 'POST', body: JSON})`로 서버에 요청한다.
3. 서버 함수가 입력을 다시 검증하고 Claude API를 호출한다.
4. 서버가 JSON을 응답하면 JavaScript가 DOM에 결과를 그린다.
5. 오류 상태 코드가 오면 서버가 준 안내 문구를 화면에 표시한다.

프론트 검증은 사용자 편의용이고, 서버 검증이 실제 방어선이다. 브라우저 검증은 우회할 수 있기 때문이다.

## Vercel Serverless Functions
요청이 들어올 때만 실행되는 서버 코드이다. 서버를 직접 운영하지 않아도 된다. `api/` 폴더의 파일 하나가 URL 하나(`api/coach.py` → `/api/coach`)가 된다. 밑줄로 시작하는 `_core.py`는 엔드포인트가 아니라 공용 모듈이다. 프론트는 정적 파일로, 백엔드는 함수로 배포된다.

## 환경 변수로 API 키를 관리하는 이유
- 키가 코드에 있으면 GitHub 공개 저장소를 통해 누구나 볼 수 있고, 유출되면 타인이 내 계정으로 과금을 일으킬 수 있다.
- 브라우저 JavaScript에 키를 넣어도 개발자 도구로 보인다. 그래서 키는 서버 함수에서만 쓴다.
- 로컬은 `.env`(Git 제외), 배포는 Vercel의 Environment Variables에 저장한다.
- 유출이 의심되면 키를 즉시 폐기하고 재발급한다. 커밋 이력에 남았다면 이력 정리도 필요하다.

## 로컬 환경과 배포 환경의 차이
- 로컬에서는 내 PC의 `.env`를 읽고, 배포 환경에서는 Vercel에 등록한 값을 읽는다.
- 환경 변수를 바꾸면 재배포해야 반영된다.
- 문제가 생기면 Vercel의 Function Logs에서 원인을 확인하고, 수정 후 `git push`하면 자동 재배포된다.

## AI가 만든 코드의 오류 대응
1. 증상을 재현한다(어떤 입력에서 어떤 상태 코드가 나오는가).
2. 브라우저 Network 탭과 Vercel 로그로 요청과 응답을 확인한다.
3. 프론트, 서버, 외부 API, 설정 중 어느 층의 문제인지 좁힌다.
4. 수정 방향을 말로 설명한 뒤 고친다.
